# Architecture coverage and evidence

This is an audit of the [published snapshot](README.md), with runtime and
data ownership as the unit of coverage. The source links below are repository
relative. Use the pinned source revision to read them in the same state as the
model. Tests listed here were inspected as evidence for the model.

## Cargo workspace ownership

The root [Cargo manifest](../../Cargo.toml) lists all 16 members. The Tauri shell
has a [separate manifest](../../clients/web/src-tauri/Cargo.toml). Crate names
below describe linked code, except where a binary is listed as a runtime.

| Crates                                                         | Ownership used by the model                                                                                                                                            |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hotsheet-server`, `hotsheet-cli`, `hotsheet-mcp`              | Runtime entry points and their reusable library code. The server and MCP can use headless orchestration and setup code linked from the CLI crate.                      |
| `hotsheet-model`, `hotsheet-ticketing`                         | File schema, Git operations, source contracts, checkout metadata, settings, coordination, and orchestration domain. Shared code is hosted inside the relevant runtime. |
| `hotsheet-index`, `hotsheet-extsync`                           | Local searchable projection and external native ticket adapters. The adapters and index can be used by headless entry points where supported.                          |
| `hotsheet-plugins`, `hotsheet-aitools`, `hotsheet-terminals`   | Tool manifests and setup, provider drive and permissions, and terminal/PTY services. The terminal crate also builds the detached broker.                               |
| `hotsheet-tls`, `hotsheet-sync`, `hotsheet-process-journal`    | Transport and native credential helpers, shared path/write/lock utilities, and durable process ownership records used across several hosts.                            |
| `hotsheet-notify`, `hotsheet-resource-claims`, `hotsheet-jobs` | Notifier and remote-change contracts, independent resource leases, and durable CI/validation/deployment observation.                                                   |

## Reconciled documentation differences

- The old overview's “one core library” describes a shared-domain intent. The
  checked-in Cargo workspace has separate domain and infrastructure crates.
- The older overview image implies the web and native clients embed the core.
  The Tauri artifact uses a WebView and Node bridge to the server. The only
  separate Swift client-like product here is the macOS screen saver, which
  consumes a file. The SwiftUI ticket clients and Android remain designs in
  the [client requirements](../06-clients.md).
- “MCP” names the stdio tool boundary. The shim proxies Rust server HTTP routes
  or uses a direct local store. The [OpenAPI contract](../contracts/v1/openapi.yaml)
  describes the HTTP surface, including shim presence routes.
- The peer-server view represents user-managed Hot Sheet hosts. Hot Sheet 2
  does not have a Small Tale-hosted product environment at this revision. CI
  and release artifacts are documented independently of product deployment.
- The HS2-MW7T1C side-branch sample explored search and ticket creation at an
  older revision. This baseline reuses the decision to pin evidence and view
  keys while auditing the published source independently.
